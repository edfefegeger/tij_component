# TIJPrinter1C — внешняя компонента 1С:Предприятие (Native API)

Управление струйным принтером (TIJ) по TCP: подключение, запуск и остановка
печати, очистка буфера, отправка данных в поля, чтение статуса.

Проект собран из присланного архива `tij_component-main.zip` с исправлением
дефектов, из-за которых компонента не подключалась в 1С.

---

## Что исправлено

| № | Дефект | Было | Стало |
|---|---|---|---|
| 1 | `GetAttachType` — тип подключения | `return 2` (`eCanAttachIsolated`) при комментарии `eCanAttachAny`. Компонента заявляла, что умеет работать **только изолированно**, тогда как на клиенте платформа подключает компоненты **не изолированно** → подключение не выполнялось | `return eCanAttachAny` (3) |
| 2 | `GetClassObject` — код возврата | `return 0` при успехе и `-1` при ошибке. По документации **0 — это ошибка**, успех — ненулевое значение. Объект не создавался даже после успешного подключения | `return 1` при успехе, `0` при ошибке |
| 3 | Динамический CRT | Импорты `MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`. Требовался Visual C++ Redistributable **x64** нужной версии, иначе `LoadLibrary` падал и метод молча возвращал `Ложь` | Статический CRT (`/MT` для MSVC, `-static` для MinGW). Импортируются только системные библиотеки |
| 4 | `SetPlatformCapabilities` | Не экспортировалась — компоненте были недоступны вывод сообщений и запрос информации о платформе | Экспортируется, возвращает `eAppCapabilities1` |
| 5 | Имя класса в `GetClassObject` | В исходной версии имя не проверялось. Проверку добавили, но она оказалась вредной: платформа передаёт сюда свое имя, строгое сравнение отбрасывало вызов, и `Новый()` сообщал «Тип не определен» | Проверка убрана, как в официальном шаблоне 1С: имя не анализируется |
| 6 | Менеджер памяти | `m_pMemory->AllocMemory()` вызывался без проверки `m_pMemory`; при неудаче выделения функция всё равно возвращала `true` | Проверка указателя и результата, корректный `false` при ошибке |
| 7 | Кодировки | `WStr2Str`/`Str2WStr` не преобразовывали строку, а усекали её побайтово — русские тексты и текст ошибок приезжали мусором | `WideCharToMultiByte`/`MultiByteToWideChar` в UTF-8 |
| 8 | Числовые параметры | Читался только `val_i32` — при передаче числа другим числовым типом значение было мусором | `GetInt()` разбирает `I2/I4/R4/R8/BOOL` |
| 9 | Утечка объекта | `new` без проверки результата | `new (std::nothrow)` + проверка |
| 10 | Упаковка | В архиве не было `MANIFEST.XML` (подключение через макет невозможно) и `INFO.XML` (карточка в справочнике «Внешние компоненты» не заполняется) | Добавлены оба файла, есть скрипты упаковки |
| 11 | Сборка MSVC | Не задан `/utf-8`, хотя в исходнике есть русские литералы; тип `tVariant_type` был объявлен как `long` | Добавлен `/utf-8`, тип задан явно как `uint32_t` |
| 12 | **Раскладка интерфейса компоненты** | `ComponentBase.h` объявлял все методы одним плоским интерфейсом. Платформа собрана по официальной структуре (три базовых интерфейса, у объекта компоненты три таблицы виртуальных методов) и вызывает методы по смещениям. Первые вызовы (`Init`, `setMemManager`, `GetInfo`, `Done`) попадали правильно случайно, а начиная с `RegisterExtensionAs` платформа обращалась не туда, и подключение молча не проходило | Заголовок приведён к официальной структуре: `IInitDoneBase`, `ILanguageExtenderBase`, `LocaleBase`, `IComponentBase`. В `IAddInDefBase` добавлен виртуальный деструктор, который в официальном заголовке объявлен первым: без него смещаются все вызовы методов платформы |

Отдельно: в присланном README была описана сборка на MinGW-w64, а фактический
бинарник собран MSVC (судя по импортам). Собирать на MinGW **можно**, но только
с флагами `-static -static-libgcc -static-libstdc++`, иначе DLL потянет
`libstdc++-6.dll`, `libgcc_s_seh-1.dll` и `libwinpthread-1.dll`, которых на
чистой Windows тоже нет — получится та же ошибка с другим списком файлов.
В этом проекте нужные флаги уже прописаны в `CMakeLists.txt`.

## Сборка

### MSVC (рекомендуется)

Из окна «x64 Native Tools Command Prompt» (для 32 бит — «x86 Native Tools»):

```cmd
build.cmd x64
build.cmd x86
```

Результат: `build\x64\TIJPrinter1C.dll` и `build\x86\TIJPrinter1C.dll`.

`build.cmd` вызывает `cl.exe` напрямую, поэтому версия Visual Studio значения не
имеет. Через CMake собирать тоже можно, но тогда имя генератора должно совпадать
с установленной версией студии (список даёт `cmake --help`), иначе выходит
ошибка `MSB8020: не удается найти средства сборки для Visual Studio 2022`:

```cmd
cmake -S . -B build\x64 -G "Visual Studio 17 2022" -A x64
cmake --build build\x64 --config Release
```

### Что должно быть установлено

Одна программа, больше ничего: Visual Studio с рабочей нагрузкой «Разработка
классических приложений на C++». Подойдёт бесплатная Community, а если IDE не
нужна, то «Build Tools для Visual Studio» с тем же набором компонентов.

- страница загрузок: https://visualstudio.microsoft.com/ru/downloads/
- загрузчик Build Tools: https://aka.ms/vs/stable/vs_BuildTools.exe

CMake, MSBuild и Windows SDK входят в эту рабочую нагрузку, отдельно их ставить
не нужно. Python, MinGW и Visual C++ Redistributable на машине сборки также не
требуются. Нужны права администратора и несколько гигабайт свободного места.

Если интернет нестабильный, в установщике выберите внизу «Скачать все, затем
установить». Для переноса установщика на другую машину собирается офлайн-макет:

```cmd
vs_BuildTools.exe --layout C:\vslayout --add Microsoft.VisualStudio.Workload.NativeDesktop --includeRecommended --lang ru-RU
```

Установка из макета выполняется тем же файлом с ключом `--noWeb`.

Про версию Visual Studio: `build.cmd` собирает напрямую через `cl.exe`, поэтому
подходит любая версия, включая Build Tools без IDE. Привязка к версии есть
только у генератора CMake: если собираете через CMake и получаете `MSB8020`,
значит имя генератора не совпадает с установленной версией студии.

MinGW-w64 в этом разделе намеренно не приводится: сборка им для сдачи не
подходит, подробности в разделе «Проверка на Linux».

### Прямая сборка через cl.exe

Это ровно то, что делает `build.cmd`; пригодится, если нужно собрать вручную или
разобраться, что именно передаётся компилятору. Запускать из окна «x64 Native
Tools Command Prompt» (для 32 бит — «x86 Native Tools»), из каталога проекта:

```cmd
cl /nologo /LD /MT /O2 /DNDEBUG /EHsc /utf-8 /W4 ^
   /I include /I src ^
   src\dllmain.cpp src\AddInNative.cpp src\TIJPrinter.cpp ^
   /Fe:TIJPrinter1C.dll /link ws2_32.lib
```

`/MT` здесь обязателен: с динамическим рантаймом (`/MD`, значение по умолчанию)
компонента начнёт зависеть от Visual C++ Redistributable и перестанет
подключаться там, где его нет или версия старая. Разрядность задаётся тем, из
какого командного окна запускается `cl`. После сборки всё равно прогоните
`check.cmd`.

## Проверка собранной DLL (обязательный шаг)

```cmd
check.cmd build\x64\TIJPrinter1C.dll
```

Что должно быть в выводе:

**Разрядность** — `machine (x64)` для 64-битной сборки, `machine (x86)` для 32-битной.
Собранная DLL обязана совпадать по разрядности с клиентом 1С, в котором
выполняется код.

**Зависимости** — только системные (ожидаемо `KERNEL32.dll` и `WS2_32.dll`,
возможны другие системные вроде `USER32.dll`):

Любые `MSVCP*.dll`, `VCRUNTIME*.dll`, `libstdc++-6.dll`, `libgcc_*.dll`,
`api-ms-win-crt-*.dll` означают, что статический CRT не применился, — на чужой
машине это даст молчаливый отказ подключения. Если `dumpbin` не найден, запускать
из «Developer Command Prompt for VS».

**Экспорт** — ровно эти имена, без искажений вида `_GetClassNames@0`:

```
DestroyObject
GetAttachType
GetClassNames
GetClassObject
SetPlatformCapabilities
```

## Проверка на Linux

Заменить 1С на Linux нельзя: платформа там работает с `.so`, а компонента —
Win32-DLL. Но всё, из-за чего `ПодключитьВнешнююКомпоненту()` возвращало `Ложь`,
на Linux проверяется — и статически, и реальной кросс-сборкой.

**Кросс-сборку нельзя отдавать в 1С.** GCC и MSVC раскладывают таблицу
виртуальных методов по-разному (разные ABI C++). Платформа 1С собрана MSVC и
вызывает методы компоненты по своей разметке, поэтому в MinGW-сборке она
обращается не к тем методам: по сообщениям на форумах первым вызывается
деструктор вместо `Init`, после чего клиент падает. Сборка MinGW пригодна
только для проверки на Linux: разрядность, экспорты, зависимости. Передавать
заказчику нужно сборку MSVC: `build.cmd`, `check.cmd`, `pack.cmd`.

| Что | Чем | Что нужно установить |
|---|---|---|
| Синтаксис, типы, сигнатуры `override` | `tools/syntax-check.sh` | только `g++` |
| Разрядность, экспорты, зависимости готовой DLL | `tools/check_pe.py` | только `python3` |
| Реальная сборка DLL под Windows | `tools/build-mingw.sh` | `mingw-w64` |
| Подключение в 1С и работа с принтером | — | Windows + 1С |

### 1. Проверка готовой DLL (в том числе собранной на Windows)

```bash
python3 tools/check_pe.py build/x64/TIJPrinter1C.dll                   # ожидается x64
python3 tools/check_pe.py TIJPrinter1C.dll --expect x86
python3 tools/check_pe.py 'build/**/*.dll' --expect any --quiet        # только итоги
```

Флаг `--expect` по умолчанию равен `x64`: если в маску попадают сборки обеих
разрядностей, указывайте `--expect any`, иначе 32-битная DLL будет помечена как
несоответствующая. Для отдельного файла просто укажите его разрядность явно.

Скрипт читает таблицы экспорта и импорта и проверяет то, что раньше было причиной
отказа: разрядность, наличие обязательных экспортов и неискажённость их имён,
отсутствие несистемных зависимостей. Код возврата 0 — всё в порядке, 1 — есть
проблемы, так что его удобно вставлять в скрипты сборки.

Для сравнения: на исходной присланной DLL этот скрипт находит `MSVCP140.dll`,
`VCRUNTIME140.dll`, `VCRUNTIME140_1.dll` и `api-ms-win-crt-*`, а на собираемой
из этого проекта — только `KERNEL32.dll`, `msvcrt.dll` и `WS2_32.dll`.

### 2. Синтаксическая проверка исходников

```bash
tools/syntax-check.sh
```

Компилятор только анализирует код (`-fsyntax-only`, предупреждения как ошибки).
Заголовки Windows подменяются минимальными заглушками из `tools/stubs`, поэтому
не нужны ни Windows, ни кросс-компилятор. Ловит опечатки, несоответствия
сигнатур и предупреждения; не проверяет разрядность и зависимости — для этого
пункт 1 или 3.

### 3. Кросс-сборка для проверки, а не для сдачи

```bash
sudo apt install mingw-w64        # Debian/Ubuntu
tools/build-mingw.sh all          # x64 и x86
```

Скрипт собирает DLL со статическим рантаймом и сразу прогоняет по ним
`check_pe.py`. Результат: `build/mingw-x64/TIJPrinter1C.dll` и
`build/mingw-x86/TIJPrinter1C.dll`.

**Эту сборку нельзя передавать в 1С на Windows.** GCC и MSVC раскладывают
таблицу виртуальных методов по-разному (разные ABI C++), а платформа 1С
собрана MSVC и вызывает методы компоненты по своей разметке. В MinGW-сборке
она обращается не к тем методам: по сообщениям на форумах первым вызывается
деструктор вместо `Init`, после чего клиент падает. Показательно, что плоские
экспортируемые функции (`GetClassNames`, `GetClassObject`,
`SetPlatformCapabilities`) при этом вызываются нормально, а вот созданный
GCC объект компоненты платформа использовать не может.

Практический вывод: кросс-сборка годится только как проверка того, что код
компилируется и что у библиотеки правильные экспорты и зависимости. Собирать
для заказчика нужно MSVC: `build.cmd`, `check.cmd`, `pack.cmd`.

Через CMake то же самое:

```bash
cmake -S . -B build/mingw-x64 -DCMAKE_TOOLCHAIN_FILE=tools/mingw-toolchain.cmake
cmake --build build/mingw-x64
cmake -S . -B build/mingw-x86 -DCMAKE_TOOLCHAIN_FILE=tools/mingw-toolchain.cmake \
      -DTOOLCHAIN_PREFIX=i686-w64-mingw32
cmake --build build/mingw-x86
```

### О повторяемости сборки

Сборка не побайтово воспроизводима: в PE-заголовок попадает отметка времени
(`TimeDateStamp`), поэтому md5 повторной сборки отличается при том же самом коде.
Сравнивать нужно экспорты и зависимости через `check_pe.py`, а не контрольные
суммы файлов.

### Чего на Linux проверить нельзя

- факт успешного `ПодключитьВнешнююКомпоненту(...) = Истина`, безопасный режим,
  режим совместимости конфигурации, разрядность клиента — только 1С на Windows;
- поведение таблицы импортов именно MSVC-сборки (у MinGW набор другой, но
  проверка читает ту же самую таблицу импорта из PE-файла);
- совместимость ABI с платформой: MinGW-сборка все проверки проходит, но в 1С
  на Windows работать не будет (см. выше);
- обмен с реальным принтером по TCP.

## Подключение в 1С

### Вариант 1: из файла (толстый клиент)

```bsl
ПутьКФайлу = "C:\TIJ\TIJPrinter1C.dll";

Если Не ПодключитьВнешнююКомпоненту(ПутьКФайлу, "TIJ", ТипВнешнейКомпоненты.Native) Тогда
    Сообщить("Не удалось подключить компоненту");
    Возврат;
КонецЕсли;

Принтер = Новый("AddIn.TIJ.TIJPrinter");
```

Имя в `Новый()` трёхчастное: `AddIn.<Имя из ПодключитьВнешнююКомпоненту>.<Имя объекта компоненты>`.
Двухчастный вариант `Новый("AddIn.TIJPrinter")` — это ProgID для COM-компонент,
зарегистрированных в реестре; для Native-компоненты из файла он не подходит.

Если платформа 8.3.21 или новее, тип подключения можно задать явно четвёртым
параметром (`ТипПодключенияВнешнейКомпоненты`) — точное имя значения смотрите
в синтакс-помощнике своей версии платформы:

```bsl
ПодключитьВнешнююКомпоненту(ПутьКФайлу, "TIJ", ТипВнешнейКомпоненты.Native,
    <ТипПодключенияВнешнейКомпоненты>);
```

По умолчанию: в режиме совместимости с 8.3.20 и ниже — не изолированно;
в остальных случаях на сервере — изолированно, на клиенте — не изолированно.
Компонента объявляет поддержку любого типа (`eCanAttachAny`), поэтому
дополнительно указывать параметр обычно не требуется.

### Вариант 2: через макет (тонкий клиент, веб-клиент, несколько машин)

1. Собрать оба варианта разрядности: `build.cmd x64` и `build.cmd x86`.
2. Упаковать: `pack.cmd` — получится `TIJPrinter1C.zip`, в корне которого лежат
   найденные сборки, `MANIFEST.XML` и `INFO.XML`. Записи `component`, для которых файла нет,
   из манифеста автоматически исключаются, чтобы `path` всегда соответствовал
   содержимому архива.

   Параметр `-MinGW64` у `pack.cmd` предназначен только для проверок на Linux:
   MinGW-сборку передавать заказчику нельзя (см. раздел «Проверка на Linux»).
3. Загрузить ZIP в конфигурацию как макет с типом «Внешняя компонента»
   или «Двоичные данные» (например, `ОбщийМакет.TIJPrinter`).
4. Подключать:

```bsl
Если Не ПодключитьВнешнююКомпоненту("ОбщийМакет.TIJPrinter", "TIJ") Тогда
    Сообщить("Не удалось подключить компоненту");
    Возврат;
КонецЕсли;

Принтер = Новый("AddIn.TIJ.TIJPrinter");
```

При подключении из ZIP-архива третий параметр (`ТипВнешнейКомпоненты`)
не используется — платформа выбирает библиотеку по `MANIFEST.XML`.

### Вариант 3: через справочник «Внешние компоненты» (БСП)

В конфигурациях на БСП прямой вызов `ПодключитьВнешнююКомпоненту` может быть
заблокирован защитой внешних компонент. Штатный путь — загрузить архив в
справочник и подключать через БСП.

1. НСИ и администрирование → Печатные формы, отчеты и обработки →
   Внешние компоненты → Добавить → Из файла, выбрать ZIP.
   Поля «Наименование», «Идентификатор» и «Версия» заполняются автоматически
   из `INFO.XML`. Идентификатор равен `TIJPrinter`, версия `1.0.0.0`.
2. Подключение из кода:

```bsl
Если Метаданные.ОбщиеМодули.Найти("ВнешниеКомпонентыСервер") <> Неопределено Тогда

    Модуль = ОбщегоНазначения.ОбщийМодуль("ВнешниеКомпонентыСервер");
    Результат = Модуль.ПодключитьКомпоненту("TIJPrinter");

    Если Результат.Подключено Тогда
        Принтер = Результат.ПодключаемыйМодуль;
    Иначе
        Сообщить(Результат.ОписаниеОшибки);
    КонецЕсли;

КонецЕсли;
```

`ПодключитьКомпоненту()` возвращает структуру `{Подключено, ПодключаемыйМодуль,
ОписаниеОшибки}`: `ОписаниеОшибки` содержит конкретную причину сбоя, в отличие
от обобщенного сообщения при прямом вызове.

Значение `progid` в `INFO.XML` задано как `AddIn.TIJPrinter`. Оно должно
совпадать с именем, которое компонента регистрирует во встроенном языке
(`RegisterExtensionAs` и `GetClassNames` возвращают `TIJPrinter`),
поэтому менять его нельзя: в поле «Идентификатор» карточки попадает часть
без префикса `AddIn.`, то есть `TIJPrinter`.

## Тестовый сценарий

```bsl
Если Не ПодключитьВнешнююКомпоненту("C:\TIJ\TIJPrinter1C.dll", "TIJ", ТипВнешнейКомпоненты.Native) Тогда
    Сообщить("Подключение: ЛОЖЬ");
    Возврат;
КонецЕсли;

СисИнфо = Новый СистемнаяИнформация;
Сообщить("Платформа: " + СисИнфо.ТипПлатформы);   // Windows_x86_64 или Windows_x86
Сообщить("Версия: "    + СисИнфо.ВерсияПриложения);

Принтер = Новый("AddIn.TIJ.TIJPrinter");

Если Принтер.Connect("10.10.0.2", 8010) Тогда
    Сообщить("Соединение с принтером установлено");
    Сообщить("StartPrint: " + Принтер.StartPrint());
    Сообщить("SendField:  " + Принтер.SendField(1, "(01)0880999084565666771(21)5/56BK"));
    Принтер.Disconnect();
Иначе
    Сообщить("Нет связи с принтером: " + Принтер.GetLastError());
КонецЕсли;
```

## Если подключение всё равно возвращает Ложь

1. Убедиться, что DLL именно та: `check.cmd` показывает только системные
   зависимости и пять экспортов.
2. Сверить разрядность: `СистемнаяИнформация.ТипПлатформы` в том контексте,
   где выполняется код (`&НаКлиенте` / `&НаСервере`), и разрядность DLL.
3. Process Monitor, фильтр `Process Name is 1cv8.exe`, `Path contains TIJPrinter1C`.
   Результат `LoadLibrary` покажет либо `NAME NOT FOUND` с именем недостающего
   файла, либо успешную загрузку — во втором случае причина в интерфейсе
   компоненты, а не в загрузке библиотеки.
4. Проверить, не включён ли безопасный режим: `УстановитьБезопасныйРежим(Истина)`
   запрещает подключение внешних компонент.

## Что не менялось

- `src/TIJPrinter.cpp` и `include/TIJPrinter.h` — логика протокола принтера
  перенесена без изменений.
- `include/AddInDefBase.h`, `include/ComponentBase.h`,
  `include/IMemoryManager.h` — интерфейсные заголовки перенесены без изменений
  (это локальные копии заголовков из комплекта ИТС).

## Известные ограничения

- `SendField` передаёт длину значения одним байтом, то есть не более 255 байт
  на поле.
- Тексты ошибок формируются драйвером на латинице; преобразование в UTF-8
  добавлено, но русских сообщений в `TIJPrinter.cpp` пока нет.
- `GetInfo()` возвращает `2000` (версия 2.0) — как в исходной версии.
